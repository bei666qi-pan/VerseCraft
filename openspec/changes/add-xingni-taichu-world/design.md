## Context

当前入口拥有轮播式世界卡片，analytics 也接受 `worldId`，但 `/api/chat` 的 prompt/guards、`useGameStore` 默认值、`RunSnapshotV2`、复活图和服务节点都直接绑定暗月公寓。仅新增入口卡片会让玄幻玩家继续收到 B1、原石、异常和第一人称暗月叙事，因此需要先形成薄而明确的世界边界。

## Goals / Non-Goals

**Goals:**

- 让世界与地图成为创建、存档、请求、事实检索和回合提交的显式身份。
- 保持单一 store 和现有 SSE/DM final 契约，通过世界适配器选择确定性规则与内容。
- 交付青石县最小可玩纵切，并使后续地图能通过目录和内容包扩展。
- 旧暗月存档和现有暗月回归测试继续工作。

**Non-Goals:**

- 不把回合工作流改成多 agent 系统，不建立第二个 store 或第二条聊天 API。
- 不在本 change 中完成第二张地图、完整修仙经济或高阶境界内容。
- 不把所有暗月模块一次性重构为完全通用框架；只抽取玄幻纵切真正使用的确定性基座。

## Decisions

### 1. 使用显式世界目录与判别式状态

新增纯数据 `worldCatalog`，以 `worldId + mapId` 解析显示信息、初始地点、地图图谱、开放状态和运行时 profile。store 保存 `worldId`、`mapId`、`unlockedMapIds` 与 `worldState`；玄幻状态使用判别式对象，避免把修为字段散落成暗月也必须理解的根字段。

选择该方案而不是通过地点前缀推断世界，因为旧代码已有别名、自然语言地点和多个默认值，推断会在迁移与恶意请求中产生歧义。旧存档缺省身份只在迁移阶段确定为暗月。

### 2. 在线回合先做世界边界校验，再选择 prompt/guard

`ClientStructuredContextV1` 增加受限 `worldId`、`mapId` 和 `worldStateDigest`。请求通过基本验证后立即解析世界运行时；未知、关闭或不属于该世界的地图走现有 SSE 降级 final。暗月继续执行既有完整链路；星逆·太初使用独立 stable prompt、地图 guard 和玄幻 delta validator。共享的 SSE、normalize、resolve/commit 外壳保持一条链。

选择 staged dispatch 而不是在每个暗月 guard 内增加玄幻条件，因为后者容易漏掉世界专属 packet，并扩大热路径分支。首版允许玄幻专属规则集中在一个纯函数 guard 中，再逐步拆分。

### 3. 青石县事实由静态内容包定义，模型只产生候选表现

地图节点、边、NPC、敌人、配方、境界上限和升仙试条件均为 TypeScript 常量并有内容校验。玄幻 `world_delta` 仅接受白名单动作：修为进度、境界、灵石、凭证、配方发现、声望、试炼状态和地图解锁；validator 根据当前状态重新计算合法结果。叙事、玩家输入或模型新增 ID 均不能成为事实源。

### 4. 复用事务骨架，不复用暗月语义

战斗结果档位、配方的输入/消耗/产出、地图邻接检查和服务前置条件可复用纯函数思想。原石、污染、稳定度、异常威胁、B1 服务、复活锚和暗月职业保持在暗月适配器。玄幻使用灵石、法器耐久、修为和凭证，避免表面改名但继续继承暗月规则。

### 5. 存档采用兼容扩展，不立刻升级快照主版本

`RunSnapshotV2` 增加可选世界字段；旧数据 normalize 后显式补暗月身份。save slot ID 使用世界命名空间，玄幻主槽为 `main:xingni_taichu`，既有 `main_slot` 保持暗月。这样无需破坏已有云存档表或一次性升级所有快照消费者。

### 6. 世界知识增加作用域并 fail closed

`world_knowledge_chunks` 增加非空 `world_id`（默认/回填暗月）和可空 `map_id`，唯一索引扩展为世界+实体+分块。检索入口必须携带作用域；玄幻无命中时只回退到玄幻 registry，不回退暗月。部署先加列与回填，再建新索引，最后启用写入与过滤。

### 7. UI 保持阅读壳层，只增加世界相关内容槽

世界选择把已存在的空卡替换为星逆卡；选择写入待创建世界并导航到带 query 的创建页。创建配置和角色面板按世界渲染，地图作为现有菜单中的轻量面板，节点点击仍提交自然语言行动。玄幻专属组件按条件导入，避免增加暗月首屏负担。

## Risks / Trade-offs

- [暗月硬编码入口众多，遗漏会造成污染] → 服务端在 prompt 组装前做世界 dispatch，并增加双向禁词/实体扫描和星逆 contract case。
- [客户端可伪造 worldId/world delta] → 世界身份与当前存档绑定，delta 由纯 validator 根据注册表和当前状态重算；客户端 digest 只作候选输入与审计。
- [兼容快照同时含暗月命名字段] → 玄幻消费者只读判别式 `worldState`；遗留字段保留但不进入玄幻 prompt 或裁决。
- [schema 迁移影响现有检索] → 新列先带暗月默认值，部署顺序可回滚；查询层在开关关闭时继续走现有暗月作用域。
- [第三人称与现有第一人称 validators 冲突] → 按世界选择 style profile/POV validator，不在共享 validator 中同时允许两种视角。
- [范围过大导致首版内容稀薄] → 只实现一个修炼、一个丹方、一个炼器、一个固定妖兽和升仙试，其他系统仅保留类型与扩展点。

## Migration Plan

1. 部署兼容类型、世界目录和读取迁移，保持新世界开关关闭。
2. 数据库增加世界知识作用域列，回填暗月并建立新索引；seed 写入显式世界/地图。
3. 部署青石县内容、store/请求字段、prompt 和 guards，仍不向玩家开放。
4. 跑暗月合同回归、玄幻 mock/E2E 和污染扫描后开启灰度。
5. 回滚时关闭开关；玄幻存档保留，暗月路径不依赖玄幻数据。数据库新增列可保留，不需要破坏性回滚。

## Open Questions

无。后续地图名称与内容在新的 change 中确定；本 change 只登记一个稳定但未开放的出口地图占位。
