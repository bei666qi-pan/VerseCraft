## F1: evaluateOffline 启发式

### 发现

`evaluateOffline` 是一个**纯启发式降级评分函数**，仅适用于无法调用 LLM judge 的场景（如快速本地迭代、单测环境）。

**来源**: `src/lib/evals/judge/judgeExecutor.ts` 第 385–437 行

```typescript
export function evaluateOffline(input: OfflineJudgeInput): JudgeVerdict {
  const { rubric, target } = input;
  const scores: Record<string, number> = {};
  const issues: JudgeIssue[] = [];
  const highlights: string[] = [];

  for (const dim of rubric.dimensions) {
    // 基于简单启发式评估
    let score = 3; // 默认及格

    switch (dim.id) {
      case "literary_quality":
        // 基于叙事长度和字符多样性粗略评估
        if (target.narrativeChars >= 300 && target.narrativeChars <= 900) score = 4;
        else if (target.narrativeChars >= 180) score = 3;
        else if (target.narrativeChars < 100) score = 2;
        break;
      case "canon_consistency":
        // 检查是否有系统提示词泄漏
        if (target.narrative.includes("系统提示词") || target.narrative.includes("JSON解析")) {
          score = 1;
          issues.push({
            dimension: dim.id,
            severity: "critical",
            description: "叙事中包含系统提示词泄漏",
            evidence: target.narrative.slice(0, 100),
          });
        }
        break;
      default:
        // 其他维度保持默认 3 分
        break;
    }

    scores[dim.id] = score;
    if (score >= 4) highlights.push(`${dim.name}：表现良好`);
  }

  const overallScore = computeWeightedAverage(scores, rubric.dimensions);
  const passed = checkPassed(scores, overallScore, rubric);

  return {
    judgeModel: "offline_heuristic",
    judgeRole: "offline",
    dimensionScores: scores,
    overallScore,
    passed,
    reasoning: "离线启发式评估（非LLM）",
    issues,
    highlights,
    timestamp: Date.now(),
  };
}
```

### 判定

- **粗糙启发式**: 是。绝大多数维度走 default→score=3，仅有 `literary_quality`（按字符数 2/3/4）和 `canon_consistency`（子串匹配 1/3）两个特殊化处理。
- **使用 actual anchor**: 否。函数完全不引用 `dim.anchors`。JudgeDimension 接口虽定义了 `anchors: ScoreAnchor[]`，但该函数只依赖 `target.narrativeChars` 和 `target.narrative.includes()`。
- 与 §2 描述一致。

## F2: scoreFixture 伪评测

### 发现

`scoreFixture` 是一个**纯结构打分函数**，评估夹具本身（fixture）的元数据字段完整性，而非 AI 输出质量。

**来源**: `scripts/eval-authenticity.ts` 第 47–60 行

```typescript
function scoreFixture(fixture: Fixture): Record<string, number> {
  const expect = fixture.expect ?? {};
  const mustNot = expect.mustNotContain ?? [];
  const persona = expect.personaMustFeel ?? [];
  return {
    canon_faithfulness: fixture.playerContext.trim().length > 0 && fixture.latestUserInput.trim().length > 0 ? 4 : 1,
    reveal_safety: expect.revealSafetyRequired && mustNot.length > 0 ? 5 : 3,
    npc_persona_distinctness: persona.length > 0 ? 4 : 3,
    task_giver_pressure:
      typeof expect.taskGiverToneMax === "number" && expect.taskGiverToneMax <= 0.5 ? 4 : 3,
    relationship_reality: /trust|relationship|active_npc|关系|信任/i.test(fixture.playerContext) ? 4 : 3,
    json_contract_validity: expect.jsonValid === false ? 1 : 5,
  };
}
```

### 判定

- **评分对象**: 确为 fixture 字段结构，非 AI 输出。函数从不调用语言模型，不读取任何 AI 生成响应。
- 每个维度使用 1-2 个条件判断，得分仅取 1/3/4/5 四个值中的两种（如 `canon_faithfulness` 只有 1 或 4）。
- 与 §2 描述一致。

## F6: 计数漂移

### 发现

`benchmarks/suite.json` 中 `game_mechanics` 轨道的声明与实际文件存在两处漂移。

#### 漂移 1: `casesFile` 路径不匹配

```
suite.json 声明: "casesFile": "benchmarks/task-eval/scenarios.json"
实际数据位于:   benchmarks/game-mechanics/scenarios.json
```

两个文件均存在且内容不同：

| 文件 | 类型 | 实际 case 数 | 说明 |
|---|---|---|---|
| `benchmarks/task-eval/scenarios.json` | Array | 10 | 较旧的任务相关用例（拾取/治疗/原石恢复等） |
| `benchmarks/game-mechanics/scenarios.json` | `{scenarios, metadata}` | 13 | 新版 5 分类 benchmark（professionx2, weaponx2, taskx2, originiumx2, combatx5） |

#### 漂移 2: `caseCount` 与实际不符

```
suite.json 声明 caseCount: 9
task-eval/scenarios.json 实际:   10 项（差 1）
game-mechanics/scenarios.json 实际: 13 项（差 4）
```

#### 另一个路径引用

`suite.json` 中 `narrative_quality` track 的 `casesFile` 指向 `"benchmarks/llm-evals/cases.json"`，该路径也需要核实是否存在。

### 判定

- **存在明显的计数漂移**。`suite.json` 的 `game_mechanics` track 在路径和计数上都未反映当前实际数据。
- 可能原因：benchmark 重构（从最初的 task-eval 10 条→game-mechanics 13 条，新增 combat 类别）后，`suite.json` 未同步更新。
