# VerseCraft 统一开发测试闭环契约 v2

> 本文件是所有功能 task 的共同工作契约。它升级 `docs/ai-dev-test-agent.md`，但在正式实施合并前不替代现有仓库规则。

## 1. 不可转移的责任

每个功能 task 的同一个 AI 必须同时承担：

- 理解需求和现状。
- 建立可复现的失败或验收基线。
- 设计和修改实现。
- 编写或修正与需求独立的测试。
- 运行自动化测试并检查真实退出码。
- 运行应用，完成与风险相称的浏览器/接口/端到端验证。
- 对发现的问题自己修改、自己复测。
- 记录证据、剩余风险和回滚方式。

禁止使用“开发已完成，等待测试 task”“代码看起来正确，测试交给后续”“测试环境有问题所以先算完成”等交接。

总控或集成 task 可以复跑集成门、审查证据并修复集成冲突，但不能替功能作者完成本应执行的自测。

## 2. 单 task 状态机

```text
UNDERSTAND
→ BASELINE
→ REPRODUCE / RED
→ IMPLEMENT
→ FOCUSED_TEST
→ ADVERSARIAL_TEST
→ APP_TEST
→ FIX
→ REGRESSION
→ HANDOFF
```

- `UNDERSTAND`：阅读 AGENTS、真实入口、上下游 contract 和任务允许路径。
- `BASELINE`：记录当前 commit、dirty state、相关测试现状和环境能力。
- `REPRODUCE / RED`：为 bug 建立失败复现；为新功能建立先失败或尚未满足的验收证据。
- `IMPLEMENT`：最小、可解释地修改生产实现。
- `FOCUSED_TEST`：先跑最小相关测试，快速发现错误。
- `ADVERSARIAL_TEST`：至少覆盖一个反例、一个边界和一个失败/恢复路径。
- `APP_TEST`：涉及可运行行为时必须启动真实应用，通过浏览器、HTTP、SSE、CLI 或数据库边界验证。
- `FIX`：测试失败后自动回到实现阶段，由同一个 AI 修复。
- `REGRESSION`：运行由风险级别决定的回归矩阵。
- `HANDOFF`：只有证据充分、已知风险明确时才可交付。

测试失败不得直接进入 handoff。循环直到通过，或出现经过证据确认、无法由当前 task 解决的外部阻塞。

## 3. 降低“自己给自己判绿”的偏差

同一个 AI 进入测试阶段时必须显式切换审查姿态：

1. 暂停继续实现，重新读取需求和验收标准。
2. 把当前 diff 当作不可信的第三方提交审查。
3. 从产品 contract 推导预期，不从实现细节反推测试答案。
4. 先找最可能失败的路径，不先证明 happy path。
5. 检查状态持久化、重试、重复点击、空输入、错误响应、权限、并发或恢复路径中与任务相关的部分。
6. 对 UI 只依据页面可见状态完成一轮黑盒操作，不通过直接读 Zustand/store/API 内部状态冒充用户测试。
7. 测试通过后检查测试本身是否真的执行、真的断言并能在缺陷存在时失败。

## 4. 测试完整性红线

禁止：

- 删除、跳过或弱化测试来让实现通过。
- 把精确断言改成“存在即可”“任意非空”而没有需求依据。
- 捕获异常后仍返回成功。
- `|| true`、固定 `passRate: 1`、失败时默认及格或不检查子进程退出码。
- 用 mock 中预埋关键词再用同一关键词判分证明质量。
- 使用未经校准的 AI Judge 作为发布硬门。
- 把 mock 通过描述为真实 AI 质量、可玩性或生产稳定性通过。
- 只截图，不验证交互后的状态和可见后果。
- 修改测试和生产代码后不说明测试为什么仍然独立可信。

若旧测试本身错误，可以修测试，但必须提供：原断言与真实 contract 冲突的证据、新断言为何更准确，以及至少一个能证明新测试不是恒真的负例。

## 5. 风险分级与最低验证

### L0：文档、注释、无行为配置说明

- 链接、命令和事实抽查。
- 格式或静态校验。

### L1：纯函数、小范围非关键逻辑

- 失败复现或新增单元测试。
- focused unit。
- 相关模块回归。
- lint/type 检查按实际影响执行。

### L2：前端、Zustand、表单、交互与普通 API

- L1 全部。
- 组件/contract 测试。
- 真实页面浏览器验证，覆盖正常、错误、重复操作和至少一个移动视口。
- 相关 E2E；不能只检查 DOM 存在，必须检查操作后果。

### L3：`/api/chat`、SSE、状态提交、存档、数据库、AI 网关

- L2 中适用项。
- SSE/JSON contract、`__VERSECRAFT_STATUS__`、`__VERSECRAFT_FINAL__`、降级和错误路径。
- store/持久化重载或迁移验证。
- mock benchmark/eval 只作为契约与稳定性信号。
- 数据库改动必须有迁移、兼容、回滚与 analytics 影响说明。

### L4：prompt、叙事质量、安全、World Director、关键玩法闭环、发布路径

- L3 中适用项。
- prompt version、缓存、packet、epistemic 和 validator 覆盖。
- 确定性安全/泄漏/状态因果检测。
- 多 persona playthrough。
- 真实模型验证只在凭证、预算和用户授权允许时执行；必须记录模型、prompt、dataset、seed、judge 和时间。
- 未经真人或校准 judge 证实，不声称“更好玩”或“叙事更好”。

全仓 `npx eslint .`、`pnpm test:unit`、`pnpm build` 不要求每个小循环都重复执行；先 focused 快速闭环，在交付前按风险运行完整门。这样既不牺牲可信度，也避免每次一行改动都耗尽反馈时间。

## 6. 环境失败处理

命令失败时先分类：

- 产品/代码缺陷。
- 测试缺陷。
- 当前改动引入的依赖或配置缺陷。
- 仓库既有失败。
- 外部环境/凭证/网络/服务不可用。

至少用一个不依赖当前改动的对照测试确认环境性问题。不得反复执行同一失败命令却没有新证据。外部阻塞必须记录原始命令、退出码、关键错误、对照证据和用户可执行的下一步；未执行的验证不能写成通过。

## 7. 并行与依赖

- 总控先建立依赖 DAG。
- 同一 parallel group 的 task 必须使用独立 worktree，且 `allowed_paths` 互不重叠。
- 每个 task 同时拥有其生产文件和对应测试文件，不能把测试文件划给另一个 task。
- 如果两个功能 task 必须修改同一入口或共享测试，则串行执行，或由唯一 integration owner 在集成窗口修改。
- 下游必须等待上游 contract 验收并形成集成 commit，而不是仅等待上游 task 发出“完成”消息。
- 测试 task 不是一种合法岗位；测试属于每个功能 task 的完成定义。

## 8. 完成定义

功能 task 只有同时满足以下条件才是完成：

1. 验收标准逐条有证据。
2. 生产改动与测试改动属于同一个 task/AI。
3. focused、adversarial、app 和 regression 中所有适用验证已执行。
4. 真实退出码和失败信息已检查。
5. 没有通过删测、降断言、fallback 及格或 mock 自证制造绿色。
6. 用户修改和范围外文件未被覆盖。
7. handoff 写明测试、未执行项、风险、回滚和 commit。
