# 夜间无人值守长跑协议（OVERNIGHT_RUN v1）

> 适用场景：用户不在场，执行者需从 PROGRESS.md 的 NEXT 起**连续执行 phase-2 → phase-6 直至完成**，中途不停等任何人工确认。
> 本文件在夜跑模式下**覆盖** phase 文件中"停下等人工确认"的要求（覆盖条款见 §2），其余一切规则（README §6 全局红线、CLAUDE.md、STYLE_BIBLE）照常有效且优先级更高。
> **另一个并行会话正在同一工作区修改"文章与任务相关"文件**，必须执行 §3 冲突协议。

---

## §1 使命与推进方式

1. 从 PROGRESS.md 的 NEXT 指针开始，按 phase-2 → 3 → 4 → 5 → 6 顺序连续执行，直到 phase-6 的 HANDOFF.md 产出为止。
2. **开工第一步（必做）**：`git status --porcelain` + `git log --oneline -15`，与 PROGRESS.md 对照，确认真实进度——并行会话可能已完成部分步骤（如 schema 里已有新表、某文案已重写）。已完成的步骤核实质量后直接勾选跳过，不重做。
3. 每完成一个编号步骤：验证 → 窄提交（§3.4）→ 更新 PROGRESS.md → 下一步。中途任何时刻被打断，账本都应能让下一个会话无缝续跑。
4. 质量纪律不因无人值守降低："不计成本"的评测迭代循环（README §7）照做；禁止为了赶进度放松阈值、跳过验证、或声称未执行的命令已通过。

## §2 人工确认点的夜跑覆盖条款

| 原确认点 | 夜跑替代动作 |
|---|---|
| phase-2 建表后 `db:push` | **仍然绝不执行 push**（含任何生产/远程库）。改为：`pnpm postgres:local` 起本地库（先读脚本确认行为与端口），在本地库上完成开发与验证；migration 文件照常生成提交；运行时对表缺失必须 fail-open（phase-2 原设计）。PROGRESS 与 HANDOFF 标注「生产 push 待人工」 |
| phase-5 前置"表未 push 不得开始" | 放宽为：**本地库可用即可开始**。生产未 push 只影响线上生效，不影响代码与测试完成 |
| phase-1 遗留 1.7 与一切 live 评测/live benchmark | 跳过，PROGRESS 标注「待人工（需网关密钥）」 |
| phase-6 6.2 CI 硬门合入确认 | 硬门 job 与去 `\|\| true` 照做并提交（本地 commit 不会自行生效到远端），HANDOFF 显著标注「醒来后 review 此提交再推送」 |
| phase-6 6.2 `VERSECRAFT_ENABLE_NARRATIVE_DIRECTIVE` 默认值翻转 | **不翻**，保持默认关（行为性变更留给用户试玩后决定）。开/关两态的 benchmark 与 e2e 证据照采集，HANDOFF 给出翻转的具体操作指令 |
| 部署环境 bump `VERSECRAFT_DM_STABLE_PROMPT_VERSION` | 无法操作部署，`.env.example` 与文档照更新，HANDOFF 列出需要设置的终值 |

## §3 并行会话冲突协议（本次夜跑的关键）

并行会话正在修改"文章与任务相关"文件，重叠风险最高的是 phase-3（开场、starter 任务文案、intro/引导文案）与 phase-5（任务戏剧化、章节 endHook）。

1. **建立避让清单**：会话开始时把 `git status --porcelain` 中已存在的未提交改动文件记为「他人领地」，写入 PROGRESS.md 的夜跑段。这些文件**只读不写**。之后每个步骤开工前重新 `git status`，新出现的、非本会话产生的脏文件同样加入避让清单。
2. **改前重读**：任何文件动手前必须重新 Read 当前内容（并行会话可能刚改过），基于最新内容做最小 diff；禁止凭本会话早期读到的旧版本直接改写。
3. **冲突时避让不硬改**：某步骤的目标文件在避让清单里 → 跳过该步骤，PROGRESS 标注「与并行会话冲突，待人工合并」，继续执行不依赖它的后续步骤。整阶段被挡住 → 跳到下一 phase 中可独立推进的部分（如 phase-3 文案被占，可先做 phase-4 的 registry 声音卡）。
4. **窄提交**：提交时逐个 `git add <明确路径>`，**永远禁止 `git add -A` / `git add .`**；commit 前 `git diff --staged --stat` 自查只含本会话文件。禁止 `git pull` / `merge` / `rebase` / `stash` 他人改动 / `git push`。
5. **共享账本**：PROGRESS.md 两个会话都在写。每次更新前重读最新版，只增改与本会话相关的行，不覆盖、不删除他人条目；基线表与 Deviations 一律追加式。
6. mockScenarios、cases.json 等评测锚若被并行会话改动导致评测红：先判断是"锚更新了"还是"真回归"——锚被有意更新则适配自己的用例，真回归则修自己引入的问题；分不清就记录 + 跳过该项验证并标注，不要盲目改回他人的改动。

## §4 阻塞与失败处理

1. **四轮上限**：同一失败（同一测试/评测项）连续修复尝试 4 轮仍红 → 停止该项，记录失败现象与已试方案，跳过并继续可独立推进的步骤。禁止无限死磕，也禁止用降阈值/删测试"解决"。
2. 环境类阻塞（本地库起不来、mock 服务端口占用等）：合理排查 2 轮，不行则跳过依赖它的验证，标注「验证未跑：环境原因」，代码与单测照常完成。
3. 破坏性红线永不因阻塞而破：不 `db:push`、不 `ship`、不 `git push`、不 `rm -rf`、不动 `.env.local`、不装新依赖。
4. 预先存在的失败（如 PROGRESS 已记录的 tsc 19 个既有类型错误）不属于本次任务，不修、不被其阻塞，汇报中如实区分。
