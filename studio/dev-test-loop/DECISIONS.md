# DECISIONS — 关键设计决策记录

> 记录设计中做出的关键决策及其理由

## D1: 不创建独立测试 AI

**决策：** 每个功能 task 的同一个 AI 必须同时承担开发、测试、修复、复测。

**理由：**
- LOOP-CONTRACT.md 明确禁止"开发已完成，等待测试 task"
- 独立测试 AI 会导致交接成本、责任分散、反馈延迟
- AGENTS.md 和所有 ai-dev-test-loop 文档一致要求同一 AI 闭环

**替代方案：** 创建专门的"测试 AI"负责所有测试。**拒绝** — 违反核心原则。

## D2: 使用状态机而非自由 Agent

**决策：** Worker 流程为确定性状态机（10 状态），不是自由 agent 协商。

**理由：**
- AGENTS.md §4.1 明确方向为 `workflow over agent`
- 状态机可追踪、可恢复、可验证
- 自由 agent 难以审计和复现

**替代方案：** 让 AI 自由决定何时开发、何时测试。**拒绝** — 不可审计，不可强制。

## D3: 风险路由替代固定测试矩阵

**决策：** 根据 git diff 自动推断风险级别（L0-L4），每个级别有不同的验证深度。

**理由：**
- 小改动不应该反复跑全部重门（浪费时间）
- 高风险改动不能逃过真实应用测试
- LOOP-CONTRACT.md §5 已定义风险分级

**替代方案：** 每次改动都跑全量测试。**拒绝** — 反馈太慢。

## D4: 文件范围互斥 + Integration Owner

**决策：** 并行 Worker 的文件范围必须互斥；共享文件由总控在集成窗口修改。

**理由：**
- 避免合并冲突
- 清晰的责任边界
- 总控作为唯一集成点保证一致性

**替代方案：** 允许 Worker 修改共享文件然后合并。**拒绝** — 合并冲突风险高。

## D5: 假绿检测器放在 Phase 2 而非 Phase 4

**决策：** 检测 `assert.ok(true)`、`test.skip(true)`、fallback 满分等假绿的检测器在第二阶段（最早实施波次）就实现。

**理由：**
- 当前代码虽然已清理了最严重的假绿（存根断言、永久 skip），但仍有隐蔽风险
- 自动化检测比人工审查更可靠
- 尽早建立完整性基线

**替代方案：** 推迟到 CI 集成阶段。**拒绝** — 越早检测越有价值。

## D6: 保留现有 test:ci 和 test:gate，逐步统一

**决策：** 不删除现有门禁脚本，而是逐步扩展 test:ci 使其与 test:gate 重合。

**理由：**
- 现有 CI 已经稳定运行
- 突变式替换风险高
- 渐进式统一允许逐步验证

**替代方案：** 用新的统一 runner 完全替换 test:ci 和 test:gate。**拒绝** — 风险太高。

## D7: judge 校准门保持 Spearman >= 0.7

**决策：** 沿用 `docs/ai-dev-test-agent.md` 中的 Spearman >= 0.7 门槛，但增加强制接线。

**理由：**
- 0.7 是合理的相关性阈值
- 当前校准基础设施存在但未接线
- 只需接线而无需改变阈值

**替代方案：** 提高阈值到 0.8 或降低到 0.6。**拒绝** — 0.7 是行业惯例。

## D8: Phase 1 不实施业务代码

**决策：** 第一阶段只做审计和设计，不写任何业务代码或工作流代码。

**理由：**
- 总控提示词明确要求"第一阶段只做审计与设计，不实施业务代码或工作流代码"
- 设计需要用户批准才能进入实施

## D9: Provenance 强制执行而非可选

**决策：** AgentTestReport 必须强制包含 provenance 字段，缺失时报告警告。

**理由：**
- 当前 provenance 基础设施存在但未被使用
- 无溯源信息的测试报告不可审计
- D02 审计确认为关键缺口

## D10: Mock 模式不能声称真实 AI 质量

**决策：** Mock eval 的结果只能标注为"契约信号"和"稳定性信号"，不能声称"真实 AI 质量通过"或"叙事更好"。

**理由：**
- LOOP-CONTRACT.md §3 明确禁止
- D02 审计确认 mock 与 eval 存在设计时耦合
- `docs/ai-dev-test-agent.md` §6 明确禁止
